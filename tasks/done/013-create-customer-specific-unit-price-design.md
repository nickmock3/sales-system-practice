# 013 得意先別単価の設計を追加する

## 目的

商品選択時に、得意先ごとの取引条件を考慮して単価を自動取得できるようにする。

まずは得意先ランクではなく、得意先別に単価を切る方式を優先して設計する。

## 背景

助言では、単価には主に以下の種類がある。

- 商品別
- 商品別・得意先別
- 商品別・得意先ランク別

このリポジトリの学習段階では、得意先ランクを先に導入すると、ランクマスタ、得意先履歴、ランク別単価、優先順位の設計が同時に増える。

そのため、まずは以下の優先順位を基本方針として設計する。

1. 商品別・得意先別単価
2. 商品標準単価

得意先ランク別単価は、得意先別単価の運用で不足が見えた段階の後続課題とする。

## 対象仕様

- `specs/sales-entry.md`
- `specs/product-master.md`
- 新規仕様候補: `specs/unit-prices.md`

## 実装内容

- 得意先別単価仕様を作成する。
- 単価マスタのデータ構造を設計する。
  - 商品 ID
  - 得意先 ID
  - 単価
  - 適用開始日
  - 必要に応じて適用終了日を持たず、履歴追加で表現する
- 商品標準単価と得意先別単価の優先順位を仕様に明記する。
- 売上登録時に採用した単価種別を保存する必要があるか検討する。
- 手入力で単価変更できる場合、採用単価と入力単価の扱いを整理する。
- 後続実装タスクに分解できる粒度まで仕様を具体化する。

## 検討項目

- 得意先別単価を商品マスタ履歴とは別テーブルにするか。
- 得意先別単価にも `ValidFrom` の履歴管理を適用するか。
- 単価未設定時に商品標準単価へフォールバックするか。
- 売上明細に採用単価の根拠を保存するか。
- 単価手入力変更を許可する場合、変更理由を必須にするか。

## テスト観点

- 得意先別単価がある場合、その単価が採用される仕様になっている。
- 得意先別単価がない場合、商品標準単価が採用される仕様になっている。
- 売上日以前で一番新しい得意先別単価を採用する仕様になっている。
- 登録済み売上の単価は、単価マスタ変更後も変わらない仕様になっている。

- `specs/sales-entry.md` を更新し、売上登録時に得意先別商品単価または商品標準単価を採用すること、売上明細へ `CustomerProductPriceId`、`IsManualUnitPrice`、`AutoUnitPrice`、`ManualUnitPriceReason` を保存する方針を追記した。
- `specs/product-master.md` を更新し、商品標準単価は得意先別単価が存在しない場合のフォールバック単価であることを明記した。
- `specs/customer-master.md` を更新し、得意先ごとの商品単価は得意先履歴ではなく得意先別単価として別管理することを明記した。
- `README.md` に主な業務仕様の一覧として `specs/unit-prices.md` を追加した。

### 採用した単価優先順位

1. 売上日以前で一番新しい得意先別商品単価
2. 売上日以前で一番新しい商品履歴の標準単価

得意先別商品単価は `CustomerProductPrices` として商品マスタ履歴とは別テーブルで管理する。

得意先別商品単価は `ValidFrom` のみを持つ履歴レコードとして追加し、`ValidTo` は持たない。

得意先別商品単価が存在しない場合は商品標準単価へフォールバックする。ただし、売上日時点の商品履歴が存在しない場合は採用単価を決定できない。

売上明細には登録時点の `UnitPrice` に加えて、採用単価の根拠として `CustomerProductPriceId`、手入力変更有無として `IsManualUnitPrice`、変更前の自動取得単価として `AutoUnitPrice`、任意の変更理由として `ManualUnitPriceReason` を保存する方針とした。

`UnitPriceSourceId` のような参照先が複数テーブルに分かれるポリモーフィック ID は使わない。得意先別商品単価の根拠は nullable FK の `CustomerProductPriceId` で追跡し、商品標準単価の根拠は既存の `ProductVersionId` で追跡する。

### 得意先ランク別単価を後続に回した理由

得意先ランク別単価を導入すると、ランクマスタ、得意先履歴へのランク紐付け、ランク別単価、得意先別単価との優先順位を同時に設計する必要がある。

現段階では、商品標準単価を基本にし、例外だけを得意先別商品単価として管理する方が学習用の実装範囲として扱いやすい。

得意先ランク別単価は、得意先別単価の運用で登録量や保守負荷の課題が見えた段階の後続課題とする。
