# 022 フロントエンドの一覧ロードと選択状態管理を共通化する

## 目的

商品マスタ画面と得意先マスタ画面で増えてきた、一覧取得・選択中ID・詳細履歴・プレビュー・古い API 応答の無視に関する状態管理を整理し、後続の税率画面や得意先別商品単価画面で同じ問題を繰り返さないようにする。

## 背景

- `frontend/src/app/products/page.tsx` と `frontend/src/app/customers/page.tsx` は、検索条件、一覧ロード、選択行、履歴ロード、登録後の再読込、API エラー表示の流れが似ている。
- 得意先マスタ画面では、選択変更時に古い履歴やプレビューが残る問題、古い API 応答が後から返る問題、登録後の再読込失敗時の表示不整合を個別に解決した。
- このまま税率画面や得意先別商品単価画面を作ると、同じ状態管理を再実装してバグを作り込みやすい。

## 対象範囲

- 一覧ロードと選択状態管理の共通化方針を決める。
- 共通 hook または共通ユーティリティを `frontend/src/lib` か `frontend/src/app/_shared` など、既存構成に合う場所へ追加する。
- 得意先マスタ画面の状態管理を、共通化した仕組みへ一部または全部移行する。
- 商品マスタ画面にも適用できるか確認し、無理に大きく変えず、リスクが低い範囲で適用する。
- 古い API 応答が現在の選択状態を上書きしないことをテストで確認する。

## 実装方針

- まず外部ライブラリを追加せず、小さな自前 hook として切り出す。
- 最初から汎用化しすぎず、以下の責務に絞る。
  - request id による古いロード結果の無視
  - 一覧ロード成功/失敗の区別
  - 選択IDの保持と、選択対象が一覧から消えた場合の選択解除
  - 選択変更時の関連状態クリア用コールバック
- 履歴やプレビューの owner 情報付き表示制御は、共通化できる部分だけ切り出す。
- 画面固有の業務ルール、表示文言、フォーム初期値、登録後の補完判断は画面側に残す。
- 既存の `apiFetch`、Zod schema、React Hook Form の使い方は維持する。

## ライブラリ導入判断

現時点では、TanStack Query や SWR のようなデータ取得ライブラリは必須にしない。

理由:

- このリポジトリは販売管理システムの実装練習用であり、状態遷移をコードで学ぶ価値がある。
- 現在の画面数では、キャッシュ、バックグラウンド再検証、重複リクエスト排除などの高度な機能はまだ必須ではない。
- 導入すると、学習対象が業務画面の状態管理からライブラリ固有の設計へ寄りすぎる。

ただし、以下が増えたら導入を再検討する。

- 同じ一覧データを複数画面で共有する。
- キャッシュ、再試行、バックグラウンド再取得、楽観更新が必要になる。
- 手書きの request id 管理やロード状態管理が複数画面に広がり、保守負荷が高くなる。
- API エラー、認証エラー、再取得の扱いをアプリ全体で統一したくなる。

## 確認項目

- `cd frontend && bun lint` が成功すること。
- `cd frontend && bun run test` が成功すること。
- 関連する E2E が成功すること。
- 得意先マスタ画面で、選択変更時に古い履歴・プレビューが残らないこと。
- 古い API 応答が後から返っても、現在選択中ではない得意先の履歴・プレビューを表示しないこと。
- 登録後や履歴追加後の一覧再読込失敗時に、成功メッセージとエラーメッセージが実状態と矛盾しないこと。

## 完了記録

### 実装内容

- `frontend/src/lib/hooks/use-list-selection-state.ts` に `useListSelectionState` を追加した。
- 共通 hook では以下を扱う。
  - request id による古い一覧ロード結果の無視
  - 一覧ロード中、一覧ロードエラー、一覧ロード成功/失敗結果の管理
  - 一覧更新時の選択 ID 維持、選択対象が消えた場合の先頭行選択、空一覧時の選択解除
  - 選択変更時に画面固有の関連状態をクリアするための `onSelectionChange`
  - 登録後補完などで使う `replaceItems` と `preferredSelectedId`
- `frontend/src/lib/hooks/use-list-selection-state.test.ts` を追加し、一覧ロード成功時の選択、選択対象消失時の切り替え、古い API 応答の無視を確認した。
- 得意先マスタ画面の一覧取得、選択 ID、一覧エラー、一覧ロード状態を共通 hook に移行した。
- 得意先マスタ画面の履歴・指定日プレビューは、選択中得意先と request id の owner チェックが画面固有の表示制御に近いため既存構造を維持した。
- 商品マスタ画面にも共通 hook を適用し、一覧取得、選択 ID、一覧エラー、一覧ロード状態を移行した。
- 商品マスタ画面の履歴取得に request id と選択中商品 ID の owner チェックを追加し、古い商品履歴 API 応答が現在選択中の商品履歴を上書きしないようにした。
- `frontend/e2e/products.spec.ts` に、古い商品履歴 API 応答が後から返っても表示しないことを確認する E2E を追加した。
- `frontend/e2e/customers.spec.ts` の既存 E2E で、一覧と履歴に同じ得意先名が表示される場合に locator が曖昧にならないよう、得意先履歴領域へ期待を絞った。

### ライブラリ導入判断

- 外部ライブラリは導入しなかった。
- 現時点の目的は、画面数が増える前に request id と選択状態の基本遷移を小さく共通化すること。
- TanStack Query や SWR のキャッシュ、再検証、重複リクエスト排除は今回の要件には過剰であり、学習用リポジトリとして状態遷移を明示的に残す方針を維持した。
