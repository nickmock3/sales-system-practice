# フロントエンドテスト方針

## 目的

フロントエンドの画面実装で、入力検証、表示状態、API 連携、主要な業務操作を継続的に確認できるようにする。

## テスト種別

### Vitest

Vitest は、フロントエンド内で閉じたロジックと軽量な UI 状態確認に使う。

主な対象は以下とする。

- Zod スキーマの入力検証
- API クライアントのリクエスト組み立てとエラー変換
- 日付、金額、税率などの表示用フォーマット
- 共通 UI コンポーネントの基本状態
- フォームの入力エラー表示

Vitest では、原則として実バックエンド API には接続しない。

### Playwright

Playwright は、ブラウザ上のユーザー操作と画面遷移を確認する E2E テストに使う。

主な対象は以下とする。

- 画面が表示できること
- 一覧、登録、履歴追加などの主要操作ができること
- 入力エラーと API エラーが画面に表示されること
- 登録後に一覧や詳細の表示が更新されること

## モック方針

### Vitest のモック

- API クライアントの単体テストでは `fetch` をモックする。
- コンポーネントテストでは、画面全体ではなく、対象コンポーネントに必要な関数やデータを差し替える。
- Zod スキーマやフォーマット関数など、外部依存が不要な処理はモックしない。
- モックデータは業務ルールが分かる最小限のデータにする。

### Playwright のモック

Playwright では、テスト目的に応じて以下を使い分ける。

- UI の分岐、入力エラー、API エラー表示を確認する場合は、`page.route` で API レスポンスをモックする。
- バックエンドとの結合を確認する場合は、ローカルのバックエンド API に接続する。

画面ごとの基本 E2E は、まずモック API で安定して確認する。
バックエンド API を使う結合 E2E は、主要な正常系に絞って追加する。

## E2E の実行方針

- Playwright はフロントエンドの dev server を起動して実行する。
- 結合 E2E を実行する場合は、バックエンド API も起動してから実行する。
- テストデータの初期化方法は、バックエンド API の実装に合わせて別途定める。
- まずは各画面 1 本以上の正常系 E2E を作る。
- エラー系 E2E は、API モックを使って画面表示を確認する。

## テスト配置

推奨配置は以下とする。

- 単体テスト・コンポーネントテスト: `frontend/src/**/*.test.ts` または `frontend/src/**/*.test.tsx`
- E2E テスト: `frontend/e2e/**/*.spec.ts`
- テスト共通データ: `frontend/src/test/` または `frontend/e2e/fixtures/`

## 完了判定への使い方

各フロントエンド画面タスクでは、少なくとも以下を確認する。

- `bun lint`
- Vitest のテストコマンド
- Playwright の対象画面 E2E

画面タスクの完了時には、実行したテスト種別、モック API か実 API か、確認できた業務操作をタスクファイルに追記する。
